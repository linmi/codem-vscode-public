# 行内补全触发与生命周期

## 问题与目标

用户反馈 macOS 快捷键没有反应或打开系统搜索。原默认 `Cmd+Alt+Space` 与 macOS Finder 搜索冲突；自动 Provider 请求被直接拒绝。建议列表展开时，原实现始终使用光标插入范围，未遵守 VS Code `selectedCompletionInfo` 的范围和前缀约束，生成结果可能不显示。

唯一入口仍为 VS Code 的 InlineCompletionItemProvider。手动命令使用 `Cmd+Alt+\`（Windows/Linux 保持 `Ctrl+Alt+Space`），先检查文件、选区、信任、开关与连接状态，再触发原生建议。无文件或 untitled 文档明确提示先保存；不扩大工作区访问范围。

自动请求默认开启，在 Provider 收到请求后防抖 250ms，需要 `editor.inlineSuggest.enabled`、`codem.completion.enabled` 和 `codem.completion.autoTrigger` 开启，且连接空闲。关闭自动开关仍保留手动入口。自动模式不创建连接、不排队等待主任务完成；下次输入再触发。生成期间显示可取消的状态栏；自动失败写日志，手动失败同时提示，不逐键弹窗。

## 状态与边界

`src/integrations/inlineCompletion.ts` 独立拥有本窗口的待触发请求、AbortController 和清理链；仅依赖聊天控制器的轻量就绪状态、上下文身份、工作区校验和生成操作。不增加持久数据、通用模型缓存、连接或反向依赖。

- 首次触发复用已连接的空闲 Core，连接缺失时手动明确提示，自动跳过。
- 重复操作取消旧请求；等待旧请求终态和清理后，仅最新请求可开始生成。取消回执不视为 Core 终态。
- 文档修改、光标移动、切换编辑器、配置变更、取消令牌和扩展销毁使结果失效；其他文档修改不取消当前请求。
- 防抖期间切换会话不发送旧上下文。模型执行期间的会话切换、断线和取消终态由既有 `ChatController.generateText` 校验与回收。
- 失败后释放所有权和状态栏，下次手动或输入可以重试。重载销毁本地状态，不恢复旧补全。结果只交给原生灰字展示，用户接受前不写文件。
- 建议列表展开时，以所选项的替换范围计算前后文，返回以所选文本开头、范围完全一致的补全。

调用链：用户输入/手动命令 → Provider（自动防抖）→ 一次工作区路径校验 → generateText → 一次授权 → 首次需要时一次 thread/start → 一次旁问。后续复用线程与连接。取消只发一次取消请求并等待 Core 终态；5 秒内未收到终态时只答复编辑器调用方，不断开聊天连接（见下文“编辑器生成占用聊天阶段”）。每次记录触发类型、总耗时和生成调用次数（调用可能在授权或取消阶段结束，不冒充服务端模型请求次数），不记录代码上下文。

外部依据：项目 VS Code 基线 ^1.105.1 / @types/vscode 1.105.0；[对应稳定 API](https://github.com/microsoft/vscode/blob/1.105.1/src/vscode-dts/vscode.d.ts) 的 InlineCompletionContext 定义了建议列表约束；[Apple 快捷键说明](https://support.apple.com/en-us/102650) 记录原快捷键的系统用途。

## 实际体验反馈

用户实际编辑时反馈等待慢、输出效果一般。宿主日志出现约 2.3–3.1 秒、10.3 秒和 14.6 秒的生成调用总耗时，以及一次内容格式/长度校验失败；旧日志未区分成功和取消，不能把所有耗时当作成功补全延迟。优化前的通用旁问仅接收语言和截断前后文，未提取相关类型/定义，也未设置独立补全模型和输出预算；Provider 等完整 JSON 与旁问终态后才交付灰字。真实 Core 简单加法测试证明链路可用，不证明真实编辑质量与延迟达标。这次反馈作为下述质量与延迟优化的基线，不能以触发链路验收替代质量验收。


## 常驻状态栏与勾选面板

原入口仅在生成期间显示，空闲时不能操作开关。新增 `InlineCompletionStatus`，仅负责原生 StatusBarItem、QuickPick 及配置读写，Provider 继续独立拥有请求和取消；不传入 Controller、不建立第二份开关状态、不新增 Webview 消息或依赖。

初始状态在 show 前由当前资源的配置确定，不依赖 Host/RPC；显示自动、手动或已关闭。生成投影为等待、生成中、取消中和失败；请求结束回到配置对应模式，失败保留到下次请求或切换编辑器。VS Code 自身关闭自动内联建议时显示手动并在提示里解释。按钮具备可访问名称，使用 VS Code 自身图标和主题。

点击打开原生多选面板，提供总开关和自动触发两个实际复选框；点击确定（输入框聚焦时可按 Enter）保存，Esc/切换编辑器放弃尚未提交的选择。保存只写发生变化的配置，目标是当前文件夹、有工作区无文件时的工作区、或用户设置，标题明确显示范围。保存中禁止重复提交，写入失败保留面板可重试并明确告知可能部分保存，不静默回滚其他设置。开关修改会走原有配置事件取消过期补全；重载从 VS Code 配置恢复，无额外缓存。

右上角按钮提供手动生成、活动请求取消和设置入口；没有活动请求时不显示取消。重复打开复用面板，关闭/销毁释放监听和控件。菜单打开和切换开关不进行认证、RPC 或模型调用；生成按钮复用既有一次生成路径。

本轮验证：Provider/状态栏 fixture 覆盖初始常驻、生成/取消/失败、配置变更、原生复选框保存与取消、失败重试、重复保存串行、编辑器切换、菜单复用、按钮路由和配置重载。真实宿主复用验收通过：重载后入口常驻，展开真实复选框，关闭自动并保存后显示手动，再次打开反映已保存值；修改总开关后 Esc 放弃，重新打开确认未写入；恢复自动后显示自动。菜单手动生成实际到达模型，完整样例末尾返回不可用内容，状态栏正确显示失败和警告（不计质量通过）。临时验证产生的文件夹配置已移除，恢复原有效配置，未修改样例内容或 SCM。模拟界面不适用；本轮未改模型生成协议。


## 质量与延迟优化（2026-09-21）

当前问题：通用提示缺少克制输出和正常弃答语义，空结果被复用的提交说明解析器当成错误；逐键重新请求并复制完整聊天快照，额外增加等待。真实 Core 首段 delta 与终态通常只差 1–2ms，主要耗时在授权和模型等待；前端流式动画无法解决这一瓶颈。

目标边界：`completionGeneration.ts` 专管有界上下文、短代码生成约束和结果校验；提交说明继续由 `editorGeneration.ts` 处理，删除原补全提示入口和混用解析路径。优先完成当前表达式/语句，通常一行、提示上限三行；硬校验 512 字符/8 行，非法或过长结果明确失败，不截断代码。空建议是正常弃答；只移除与已有后文完全一致的边界重叠，保留有意义的空格。上下文最多包括前文 5000、后文 2000、远处文件头 1500 字符，帮助使用本文件类型和导入；不宣称具备跨文件语义检索。

状态所有权与完整交互：

- Provider 仍唯一拥有请求、取消链和 deadline。自动防抖降为 250ms；进入生成后自动 4 秒、手动 10 秒发起取消，等待 Core 终态才能释放连接。4 秒不是清理完成时间；终态缺失仍用已有 5 秒恢复机制关闭连接。状态栏显示取消中和超时，自动超时不弹窗；手动超时明确提示，可再次触发。
- `CompletionContinuation` 只保存本窗口最近一次建议，最长 15 秒、不持久化。相同文档/版本/光标/会话/模型/思考强度下，精确输入建议前缀后，立即返回剩余部分，不再授权或调用模型。新模型请求仍逐次授权。空建议也可在相同位置去重；手动触发总是重新生成。
- 文档其他位置编辑、替换/删除、不同输入、选区、光标/编辑器切换、设置改变、取消和销毁清除候选；会话/模型身份不匹配立即失效。重载仅恢复已有开关配置，不恢复代码候选。失败无候选，下次操作可重试。接受仍由 VS Code 原生灰字/Tab 完成。
- `ChatController.completionContext()` 只返回就绪标志和身份，不再为频繁编辑器回调复制聊天记录。无循环或反向依赖；请求状态与候选状态可独立测试。

调用成本：新建议仍为一次工作区校验、一次授权、首次至多一次 thread/start、一次 side question、零 Agent turn；相同建议的剩余文本复用为零 RPC/授权/模型调用。没有新增长期认证缓存、独立连接或模型配置。每次记录自动/手动、完成/取消/失败/超时、总耗时及生成调用次数，不输出代码。

可判定准出：精确输入复用零请求；不匹配条件不能复用；自动 4 秒后取消且迟到内容丢弃，用户主动取消不误记超时；空结果不弹错误；重复括号不会写入；真实 Core 八个固定场景全部满足语义断言（TypeScript 同时解析完整前后文）；记录首段、授权和总耗时，禁止拿取消耗时当作成功延迟。

真实 Core 对照命令：`pnpm --filter codem test:live --inline-completion --baseline` 与 `pnpm --filter codem test:live --inline-completion`。八场景包含类型表达式、已有闭括号、类型属性、异步 JSON、Python 函数体、泛型数组、完整文件弃答及保留后续语句。最终对照结果：

| 提示版本 | 通过 | 中位数 | 本轮 p95（8 例中最大值） | 旁问 / Agent turn |
| --- | --- | --- | --- | --- |
| 旧提示基线 | 8/8 | 1648ms | 2272ms | 8 / 0 |
| 新实现 | 8/8 | 1574ms | 2351ms | 8 / 0 |

新实现授权耗时约 319–908ms。前一轮基线曾在完整文件后追加无关 `isOdd` 函数，新实现两轮均正常弃答，但小样本不能推导普遍成功率。首轮数组用例误拒绝等价三元表达式，修正语义断言并重跑以上对照；不将首次失败表述为通过。两轮速度有波动，当前证据不支持显著降低模型推理延迟的结论。已确定减少的是固定防抖 350ms、精确续写的重复请求及超长等待；尚不能宣称所有语言/项目或亚秒级响应达到“优秀”。Core 0.8.44 的现有旁问边界没有已核实的独立补全模型、推理预算或输出 token 预算，本轮不伪造参数。

- 模拟界面：不适用，本轮没有 Webview 变更；原生状态投影由 fixture 覆盖。

### 自动补全取消误报为聊天警告

用户截图显示“旁路提问回执未能确认；内容保留，不自动重试”。实际宿主日志连续记录输入导致的 `sideQuestion: 生成已取消`，对应自动请求约 477–595ms。根因是在授权等待期间取消后，通用旁问 catch 无条件写聊天 notice；不仅是文案问题，代码生成还把提示词、增量答案、操作回执写进用户旁问的 UI 状态。

修复边界：活动旁问由 Controller 一处保存 `kind: chat | generation`、状态和答案，Webview 的 sessionTools 仅投影用户聊天旁问。生成请求的开始、增量、成功、失败、取消与取消 RPC 失败均不改聊天 notice、旁问内容和操作回执；生成结果/错误交还原生调用方。授权阶段的正常取消不记录成旁问错误；连接断开/认证失效仍保留全局提示。Core 的终态等待、恢复与逐次授权不变，公开协议和持久历史边界不变。

回归复现了“授权尚未完成 → 输入取消 → 授权结束”，验证零旁问请求、无聊天警告且不暴露代码提示词；同时覆盖生成成功、模型失败和取消 RPC 失败不覆盖用户已有旁问及 notice，真实用户旁问原有错误/取消/快速终态行为继续通过。真实宿主未重载这个追加修复，遵守用户正在使用窗口的要求；最终构建需要用户方便时执行“开发人员：重新加载窗口”后生效。

追加修复后的完整 `pnpm check` 与正式构建再次通过；真实 Core 八场景再次全部通过，中位数 1357ms、最大值 2963ms，仍为八次旁问、零 Agent turn。补充迟到启动回执回归，验证取消中不会被回执改回运行或重复发取消请求，相关 93 个 Controller/能力测试通过。这个结果继续表明推理延迟有波动，不能宣称延迟已稳定低于一秒。

### 编辑器生成占用聊天阶段

问题：`generateText` 与聊天旁问共用 `startQuestion`，把聊天切到 `sideQuestion` 阶段。自动补全、下一处修改、提交说明和修改建议生成期间，发送返回失败，新建会话、模型/权限菜单和历史等控件被禁用且无说明；取消后 5 秒未收到终态就关闭整个连接，45 秒超时也走同一路径。

Core 约束：App Server 每个线程同一时间只允许一个轮次或一个旁问（`turn/start`、旁问、压缩/回退、clear、归档等控制和变更设置的 resume 都会拒绝或先取消活动旁问）。因此编辑器请求继续借用当前线程的旁问位，但让位于聊天：

- 编辑器生成由 Controller 的独立记录持有（操作 ID、线程、旁问 ID、答案、取消原因和释放信号），不写聊天阶段、notice、sessionTools 或旁问投影；聊天旁问只保存用户自己的问题。
- 发送、聊天旁问、压缩/回退、shell、当前线程的会话管理、设置变更、新建会话、切换历史和原生建线程先回收旁问位：发一次取消请求，最多等待 5 秒 Core 终态；超时则本次聊天操作不执行并显示“编辑器生成尚未结束”，草稿保留、连接不断开。被回收的编辑器调用方收到“聊天开始了新操作，编辑器生成已取消”。发送与压缩/回退先等待让位、再占用轮次，等待期间 Core 自行开始的轮次不会被当成本次提交。
- 取消（输入、手动、45 秒超时）只发一次取消请求；5 秒内无终态时答复调用方，旁位继续保持到 Core 终态、线程关闭或连接退休，期间编辑器请求以“另一项编辑器生成仍在进行”拒绝，聊天操作按上一条处理；新建会话在等待超时后仍释放该线程（App Server 连同旁问一起遗忘），无需重连。
- 空白会话首次生成仍会创建会话线程，但只在聊天空闲时创建；授权期间聊天已开始目录读取、粘贴等操作时编辑器让位，不改动会话身份。`thread/start` 改为单飞，聊天与编辑器并发时只创建一次，目录读取等待进行中的首个线程，创建后立即发布会话身份。
