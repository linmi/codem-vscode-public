# 聊天控制器职责拆分

## 目标与不变量

当前控制器同时保存轮次协调、资源句柄、后台任务和历史读取状态，资源清理与异步失效必须修改同一个类。本轮逐个迁移这些边界；不改变公开聊天操作、Webview 消息协议、Core 终态规则或持久化格式。

- 控制器保留连接、当前会话身份、轮次及跨功能操作的准入与协调。
- 会话资源模块拥有附件、图片读取器、文件搜索、产物和 Diff 句柄；只输出展示投影，不获得 Controller 或可写 ChatSnapshot。
- 后台任务模块拥有进程/任务句柄、刷新互斥与轮询清理；绑定明确的会话上下文，旧上下文结果不能提交。只有用户发起的终止、清理和任务取消占用聊天的 `backgroundBusy` 互斥；3 秒轮询和手动刷新只读取、不发布忙碌，轮询不与进行中的读取叠加，手动刷新总是读取且最新读取生效，列表未变化时不发布快照。
- 历史读取模块拥有读取令牌、分页游标、恢复事务和取消；控制器只在事务成功后提交当前会话与展示内容。

首次使用仍按需连接；重复操作沿用互斥规则；取消与失败不消费草稿、不自动重发。历史恢复失败保留原会话；订阅状态不确定时断开连接。新会话、空间切换、断线及退出时清理对应临时状态；Webview 重载不重建 Host 会话。所有模块均不增加持久化缓存。

昂贵操作保持原调用链：发送按需连接后 thread/start → turn/start；恢复历史 authorize → thread/read → thread/resume → modes/read → 本地历史读取 → 释放原订阅；后台刷新只调用一次 terminals/list，终止/清理后再刷新一次。拆分不新增认证、RPC 或子进程。

## 验证

每个边界独立验证状态规则和取消/过期结果，保留控制器集成测试。最终运行默认检查、正式扩展与原生 Chat 构建；模拟界面、真实 Core 和真实 VS Code 验证分别记录，不用构建或 fixture 替代。

## 交付边界

| 模块 | 唯一拥有的状态 | 清理与失效 |
| --- | --- | --- |
| `resources/conversationResources.ts` | 附件、图片读取器、搜索/产物/Diff 句柄及资源版本 | 会话重置清理全部；首次连接可明确保留草稿附件；异步校验/搜索/读取拒绝旧版本 |
| `chat/backgroundTasks.ts` | 进程和任务句柄、变更互斥、读取互斥、轮询计时器、操作版本及读取序号 | 会话切换清理状态；连接退休停止计时器；旧操作不能发布或解除新操作互斥；较新的读取、用户变更或会话切换使晚到的旧读取结果作废 |
| `sessionHistory/conversationHistory.ts` | 历史读取租约、候选恢复订阅和分页游标 | 实时轮次中止读取但保留租约直到清理完成；连接退休重置；释放候选订阅失败要求断开 |
| `chat/chatController.ts` | 连接/会话身份、当前轮次、设置与跨模块准入 | 协调连接退休及会话提交；不再保存上述模块的私有 Map、计时器或读取令牌 |

设置与模型菜单正由并行任务调整，本轮没有迁移设置所有权。控制器仍承担当前轮次和设置的协调；本次不声称所有职责已从该类移出。传给历史模块的是有限的 Host 读取能力及上下文有效性断言，传给后台模块的是当前线程的后台能力，不传可写 Controller 或 ChatSnapshot。展示快照是模块结果的投影，不是第二套业务状态。

资源投影在现有 `historyMessages`、`Artifacts`、`FileReferences` 实现上组合；这些实现没有复制。`UserVisibleError` 已移到纯共享契约并原子更新调用方，无旧路径再导出。

## 验收记录

- 单元/集成：资源原子添加、失败保留、权限撤销、资源重置、附件身份保留；后台操作 RPC 次数、重复请求互斥、失败重试、旧请求晚到、计时器停止；历史恢复 RPC 顺序、候选订阅清理、实时事件中止、旧读取晚到、重复游标、发布期间失效，均有独立测试。原控制器和历史集成继续通过，补充新建会话不能绕过旧读取清理的回归。
- 默认门禁：当前组合工作树 `pnpm check` 通过，包含架构正反例。三个状态模块不能反向引用 Controller、界面容器或应用入口；运行时别名解析与静态类型导入分别验证。
- 提交隔离：另建无 GUI 的临时源码快照，仅包含本轮变更，独立执行 lint、Host/Webview/Composer 类型检查、全部扩展测试与两种构建，避免以并行菜单变更弥补本轮提交缺失。复用现有依赖，不安装依赖或启动应用。
- 模拟界面：本轮未执行，Webview 渲染及消息协议未改动。
- 真实 Core：本轮未运行；RPC 次数与失败恢复依据协议 fixture，未宣称真实模型验收。
- 真实 VS Code：本轮未执行；未新增或重载用户窗口。
- 迁移检索：Controller 已无资源 Map、后台计时器、历史游标/读取令牌；相关命中只存在于对应所有者。生产模块无反向 Controller 引用；架构测试中的反向引用是预期负向 fixture。

## 后台轮询不再占用聊天互斥

问题：空闲会话每 3 秒轮询一次后台终端，原 `run()` 与终止/清理共用互斥，每次轮询把 `backgroundBusy` 置为真并发布三次完整快照。Controller 中 16 处准入读取该标志，新建会话、模型与权限菜单、历史和后台按钮随之每 3 秒闪烁禁用，窗口期内的点击被静默丢弃；轮询失败还会每 3 秒覆盖聊天 notice。

修复：读取与变更分开。读取不改 `backgroundBusy`；轮询在已有读取时跳过，手动刷新总是发起读取（不被轮询吞掉），最新读取生效；轮询失败只写日志，手动刷新失败才提示。终止、清理和任务取消仍占用互斥（发布忙碌、执行、刷新一次列表、解除）。每次读取取得序号，变更开始或更新的读取会使旧结果作废，会话切换沿用版本号作废。

调用次数：每次轮询仍为一次 `terminals/list`；发布由每次 3 次降为列表未变 0 次、变化 1 次；慢轮询不叠加。终止/清理/取消仍为一次变更 + 一次 `terminals/list`。

验证：新增回归覆盖轮询不改忙碌且列表未变不发布、慢轮询不叠加、变更后晚到的轮询结果作废、会话切换后旧读取不释放新读取，空闲会话轮询期间新建会话不被丢弃，以及慢轮询期间手动刷新仍读取、结果胜出并报告自身失败；新增用例在原实现上失败。`pnpm check` 与 `pnpm build:vscode` 通过。模拟界面未运行（Webview 未改动，快照序列由测试断言）；真实 Core 受阻（`codem-auth auth status` 报告未登录）；真实 VS Code 未运行（同一登录前提，没有可复用的开发宿主，未新开窗口）。

## 流式快照的发布成本

问题：流式回复每个增量发布一次聊天快照。`snapshot()` 对整个状态（含全部消息正文）做 `structuredClone`，每个 token 都按会话长度付一次复制。控制器本就只替换状态、不就地修改，这次复制只起防御作用。

修复（Host）：快照与上一份共享所有未变化的对象，发布时由 `src/shared/frozenSnapshot.ts` 只冻结本次新建的对象，已冻结的子树直接跳过，消息正文不再复制；历史列表同样直接返回自身不可变的状态。已发布数据只读：就地修改会抛错，控制器全部测试在冻结下运行。没有新增缓存。

测量：`node --experimental-strip-types apps/vscode/scripts/benchmarkSnapshots.ts` 在无 Core、无 VS Code 的 fixture 上逐段计时（Host、模拟 postMessage 的 JSON 往返、Webview bridge、ChatApp `asSnapshot`）并计数。501 条消息（每份状态约 597 KiB）× 200 个增量：Host 每增量中位数 0.36 ms → 0.05 ms，整状态克隆 1 → 0 次，重新创建的未变消息约 498 → 0 条。

验收：`snapshotPublishing.test.ts` 在 10 条与 500 条消息下断言每个增量整状态克隆 0 次、未变消息重建 0 条，已发布快照深度冻结且不随后续增量变化，未变的消息、历史列表与能力区在前后快照间是同一对象；两项在原实现上均失败。

字段读取：控制器 12 处收尾判断用 `this.snapshot().phase`（为绕开 TypeScript 对 `this.state.phase` 的收窄），扩展入口 6 处 `chat.snapshot().threadId` 与 1 处 `chat.snapshot().phase` 只为读一个字段。原实现每次读取克隆整份状态（501 条消息约 0.37 ms），去掉克隆后仍需构建并冻结一份快照（约 1.1 µs）。改为 `phase()` 与 `currentThreadId()` 直接读取（约 0.03 µs）；`phase()` 是方法调用，不受先前收窄影响。测试断言这些操作构建的快照数等于发布数，把收尾判断改回 `snapshot().phase` 时失败（构建 11 次、发布 8 次）。

修复（Webview bridge）：`project()` 原先对整份投影做 `JSON.stringify` 只为判断是否递增 version，再由 `asSnapshot` 重新规范化全部消息。现在保存上一次投影：同一位置的 Host 消息逐字段相同则复用其冻结的规范化结果，只规范化变化的消息；其余部分逐字段比较，内容变化才递增 version，判定与原 JSON 签名一致。缓存范围是单个 bridge 实例（一个 Webview 页面）的最近一次投影，每次投影整体替换；Host 消息与上次逐字段不同即重新规范化。测量同上：bridge 每增量中位数 0.58 ms → 0.12 ms，序列化 597 KiB → 0（仅剩会话范围元组），重新规范化的未变消息约 498 → 0；剩余线性部分是逐条比较消息正文，不分配、不序列化。

验收：bridge 在 10 与 500 条消息下每个增量序列化字节相同且少于 256，未变消息重新规范化 0 条，version 每个增量加 1；另一测试逐步比较增量投影与全新 bridge 对同一 state 的投影（除 version 外完全相同），并断言相同 state 不递增 version、只变提示时消息全部复用、未知角色仍被丢弃、共享结果冻结且不含路径。原实现上前者失败（序列化 610278 对 12499 字节），后者只在复用断言处失败，语义断言通过。

修复（界面 `asSnapshot`）：`normalizeMessages` 对深度冻结的消息对象复用它冻结的规范化结果。规范化只取决于消息本身，深度冻结的消息不会再变，结果不会过期。复用表是 `packages/ui/src/contract.ts` 模块内的 WeakMap（一个页面），键为弱引用、随消息对象回收；未冻结的输入（JetBrains 等每次新解析的 JSON）照旧每次重新规范化，结果不冻结。VS Code bridge 交出的消息正是冻结的、没变即同一对象，因此没变的消息在 ChatApp 的快照里也保持同一对象。测量：ChatApp `asSnapshot` 在 501 条时每增量 0.08 ms → 0.04 ms，重新规范化的未变消息约 498 → 0；`ui.test.ts` 断言同一冻结消息得到同一冻结结果且与规范化副本相同，可变输入、只浅冻结的输入不复用，未知角色仍被丢弃，原实现上失败。

仍随会话长度线性的部分：VS Code postMessage 仍序列化整份快照（模拟 JSON 往返 501 条时约 1.2 ms/增量，是剩余最大项），要与变化量成正比需要 Host 只向 Webview 发送变化的消息，属于协议改动，不在本次范围；消息列表渲染没有按消息复用。
